# SparkEngine — Research Frontier and Methodology

Runbook for doing **disciplined frontier research** in SparkEngine: surveying what other
engines do, evaluating libraries and techniques, designing experiments with reproducible
local evidence, and moving findings through an explicit maturity ladder. Verified
2026-08-23 against the working tree of branch `claude/whole-nine-yards-20260823`
(uncommitted changes ahead of `0e1fe7e7`). Default upstream branch is **`Working`**.

**Jargon, defined once:**
- **Frontier research** — structured study of techniques/engines/libraries *outside* this
  repo (Unreal, Godot, Bevy, EnTT patterns, papers) to decide what SparkEngine should do next.
- **Evidence anchor** — a file, test, or command inside this repo that proves a claim.
- **Maturity ladder** — the seven states a piece of work can honestly occupy
  (idea → prototype → candidate → implemented → tested → CI-enforced → release-ready).
- **Readiness contract** — the generated ledger in `docs/readiness/` +
  `docs/site/readiness.json` that gates the word "release-ready".
- **AUTO: section** — a wiki region regenerated by `docs/sync-wiki.sh`; never hand-edit.

## When NOT to use this skill

| You are actually doing… | Use instead |
|---|---|
| Implementing the researched feature in a subsystem | The domain sibling (`sparkengine-rendering-rhi-rendergraph-and-shaders`, `sparkengine-ecs-lifecycle-threading-and-memory`, `sparkengine-modules-sdk-abi-and-hot-reload`, `sparkengine-editor-scenes-and-reflection`, …) |
| Adding/bumping a third-party library, CMake, CI matrix | `sparkengine-build-ci-and-dependencies` |
| Updating README/wiki/site wording, regenerating docs, public numeric claims | `sparkengine-docs-wiki-and-generated-truth` |
| Deciding whether something ships / gate verdicts / PR readiness | `sparkengine-change-control-and-release-readiness` |
| Diagnosing a live bug found during an experiment | `sparkengine-debugging-playbook` |
| "Didn't we already try this and it failed?" | `sparkengine-failure-archaeology` |
| Writing/interpreting tests for an implemented feature | `sparkengine-validation-and-qa` |

## 2. Research method — the five non-negotiables

1. **Verify against the tree before recommending.** The repo's own research pages found
   that a large fraction of "obvious" recommendations already existed (change detection,
   AOI, parallel scheduling; 8 of 15 workflow features). First command of any study:

   ```bash
   grep -rn "TheClassOrConcept" SparkEngine SparkEditor GameModules Tests --include='*.h' --include='*.cpp' -l
   ```

   Audit history warning (from `wiki/advanced/Stub-and-Abandoned-Features.md`): agents
   historically **under-report references** — re-grep including `Tests/`, `GameModules/`,
   and `SparkEditor/` before declaring anything "unused" or "missing".

2. **Prefer primary sources.** Cite upstream repos, official docs, source code, and
   papers — not blog summaries. For a library/API question, fetch current upstream
   documentation rather than trusting memory; APIs drift. Record the exact version/commit
   you evaluated in the wiki page.

3. **Distinguish what exists from what works.** SparkEngine contains deliberate
   API-surface stubs (VRSystem, SteamTransport, several ThirdParty stub headers — see
   `wiki/advanced/Stub-and-Abandoned-Features.md` and the stub-status note in
   `wiki/research/Third-Party-Library-Evaluation.md`). "Compiles and links" is not
   evidence of capability. Check for banner comments ("This is a STUB header"),
   `Initialize()` returning false, and whether `tools/check-wiring.sh` sees a caller.

4. **Every recommendation gets a verdict + effort + hook.** House format
   (from `Engine-and-Renderer-Landscape.md` / `Advanced-Techniques-Catalog.md`):
   - Verdict: **strong** (verified gap, do it) / **plausible** (real but speculative or
     dependent) / **considered and skipped** (already exists — say where).
   - Effort: low / medium / high *relative to existing machinery*.
   - Hook: the exact file/directory where it would land (e.g. "extend
     `Graphics/CachedShadowAtlas.h`; wire a pass into `Graphics/RenderGraph/`").

5. **Date-stamp everything.** Status markers rot. Every table carries a
   "verified YYYY-MM-DD" note, and the page ends with `## Source & Freshness`.

## 3. Experiment and benchmark methodology

A claim of "faster / better / feasible" needs a reproducible local measurement, not a
citation. The repo ships the tooling:

### BenchmarkFramework (in-engine, baseline-comparing)

- Source: `SparkEngine/Source/Utils/BenchmarkFramework.h` / `.cpp`;
  wiki: `wiki/advanced/Benchmark-Framework.md`; tests: `Tests/TestBenchmarkFramework.cpp`.
- Implement `Spark::IBenchmarkScenario` (`GetName`, `Run` → `std::vector<BenchmarkMetric>`,
  `GetIterationCount`), register via `BenchmarkFramework::GetInstance().RegisterScenario(...)`.
- Two built-in canaries register at startup: `cpu.sort_1m` and `mem.churn_4k_x10k`.
- Console commands (via SparkConsole): `benchmark.status`, `benchmark.run`.
- Baselines carry a `tolerancePercent` (default 5%); comparisons yield per-metric
  `RegressionDetail`. Each `BenchmarkMetric` declares `lowerIsBetter` — get the direction
  right or the regression check inverts.

### Full-engine load test (macro benchmark)

- `Tests/TestEngineLoadTest.cpp` — 3,000 heavy frames across 25+ subsystems, plus adverse
  and severe scenarios (`LoadTest_Severe_EntityFlood`, `LoadTest_Severe_EventBusStorm`, …).
- Baseline numbers: `wiki/advanced/Load-Test-Baseline.md`. Numbers there are
  platform-specific (Linux x86_64 / GCC Release / NullRHI) — **re-capture on a controlled
  machine before treating as a gate**.

### Running targeted experiments

```bash
# Configure + build (pick your platform preset; see CMakePresets.json)
cmake --preset linux-gcc-release          # or: cmake --preset windows-release
cmake --build --preset linux-gcc-release

# Full suite
ctest --test-dir build/linux-gcc-release --output-on-failure   # add -C Release for VS

# One test file, directly (SparkTests env-var filters — full selector list:
# sparkengine-validation-and-qa §3):
SPARK_TEST_FILE=TestBenchmarkFramework ./build/linux-gcc-release/bin/SparkTests
SPARK_TEST_NAME=LoadTest_FullEngine ./build/linux-gcc-release/bin/SparkTests
```

(Preset builds land in `build/<preset>/bin/`; a raw `cmake -B build` layout uses
`build/bin/`, with a `bin/<Config>` subdir possible under the MSVC multi-config generator.)

### Experiment design rules

- **A/B on the same machine, same config, same commit.** Record both numbers and the
  commit hash in the write-up. Never compare across platforms or build types.
- **Ask what a broken run looks like.** A benchmark that measures a stubbed path, an
  aborted build, or 0 iterations reports a reassuring number. Confirm iteration counts
  and that the exercised code path is the real one (grep the scenario's call chain).
- **Headless is fine, but say so.** NullRHI/headless numbers measure CPU-side cost only;
  label them as such (the Load-Test-Baseline page models this scoping header).
- **Prototype branches never merge as-is.** A prototype exists to produce a number and a
  design note; the production implementation is a fresh, bounded change owned by the
  domain sibling.

## 4. The maturity ladder — decision rules

Use these exact labels. Each state has a required evidence anchor; promotion without the
anchor is the failure mode this skill exists to prevent.

| State | Meaning | Required evidence in-repo |
|---|---|---|
| **idea** | Named possibility, no verification yet | A line in a `wiki/research/` page, marked **Open** |
| **prototype** | Throwaway code produced a measurement or design insight | Branch/diff + recorded numbers (commit hash, machine, config) in the research page |
| **candidate** | Verified gap + verdict + effort + named hook; worth scheduling | Research-page entry with **strong/plausible** verdict, "verified YYYY-MM-DD", and grep-confirmed hook files |
| **implemented** | Real code, wired in (Initialize called, update ticked, sink has a source) | Source files + `tools/check-wiring.sh` clean for the new system |
| **tested** | Dedicated tests pass locally | `Tests/Test<Feature>.cpp` registered in `Tests/CMakeLists.txt`; `ctest` green |
| **CI-enforced** | A *required* CI job fails closed on regression | Job in the CI matrix **without** `continue-on-error` (advisory-only, do not count: `build-linux-msan`, `build-windows-vs2026`, `build-linux-mingw-wine`, `build-macos`; `clang-tidy` *is* blocking — gate fine print: `sparkengine-validation-and-qa` §10) |
| **release-ready** | Passes the readiness contract's gates | Owned by `sparkengine-change-control-and-release-readiness`; ledger in `docs/readiness/` — **never self-award this label** |

Promotion rules inherited from the readiness contract
(`docs/readiness/ENGINE_READINESS_HANDOFF.md`, generated from `docs/site/readiness.json`
and `docs/readiness/work-items/*.json` via `tools/site-data/render_handoff.py`):

- Implementation, verification, support, and release are **independent dimensions**;
  never infer one from another.
- A passing test must execute production source or a packaged binary — mirror-only,
  tautological, or mock-only tests cannot promote anything.
- Every public numeric claim resolves through a generated metric with an evidence path.
- "Production-ready" wording is forbidden while the global release state is blocked
  (it currently is: global release `blocked`, 0 of 18 gates passing, verified
  2026-08-23 — canonical counts live in `sparkengine-change-control-and-release-readiness`).

Additional labels already in repo use — keep them consistent:
- **Implemented / Partial / Open** — per-technique status in `Advanced-Techniques-Catalog.md`.
- **experimental** — CMake's word for the non-D3D11 backends
  (`CMakeLists.txt` lines 125–127: `ENABLE_VULKAN`/`ENABLE_OPENGL`/`ENABLE_METAL`
  "(experimental)"). Research write-ups must not upgrade "experimental" to "supported".
- **stub** — API surface with a no-op body; catalogued in
  `wiki/advanced/Stub-and-Abandoned-Features.md`.

## 5. From finding to bounded work (hand-off protocol)

1. **Write the research page** (or update an existing one — prefer updating) under
   `wiki/research/`, using `wiki/_Template.md`. Verdicts, effort, hooks, dates.
2. **Add to sidebar + sync:** edit `wiki/_Sidebar.md`, then `docs/sync-wiki.sh sync`;
   check nav with `tools/check-wiki-nav.sh`.
3. **Scope the smallest shippable slice.** Anti-bloat checklist applies (search first,
   name the caller, no future-proofing, no unwired systems). One candidate → one bounded
   change, not a program of work.
4. **Route the implementation** to the domain sibling; route any new dependency to
   `sparkengine-build-ci-and-dependencies` (license must be permissive; manifest and
   `ThirdParty/` rules live there); route wording/claims to
   `sparkengine-docs-wiki-and-generated-truth`.
5. **Close the loop.** After the slice lands, update the research page's status marker
   (Open → Partial/Implemented) in the same effort — stale "Open" markers cause duplicate
   research.

## 6. Failure modes (each has occurred here)

| Failure mode | Symptom | Countermeasure |
|---|---|---|
| **Rebuilding what exists** | Recommendation for a system already shipped | Grep-verify first; record "considered and skipped — exists at `<path>`" |
| **Stub inflation** | Stub/experimental feature described as capability | Check banner comments, `Initialize()` return, wiring; label per §4 |
| **False-orphan deletion** | "Zero references" claim on a wired system | Audits under-report; re-grep with `Tests/ GameModules/ SparkEditor/` included |
| **Benchmark of nothing** | Great numbers from an unexercised or 0-iteration path | Verify iteration count and the real call chain; ask what a broken run would print |
| **Cross-config comparison** | "2× faster" comparing Debug vs Release or two machines | Same machine, config, commit; record all three |
| **Aspirational status drift** | Wiki says done, ladder says candidate | Date-stamped status markers; only §4 evidence promotes |
| **Research without a hook** | Recommendation nobody can act on | Every candidate names its landing files |
| **Unbounded adoption** | "Integrate library X" becomes a month of churn | Smallest shippable slice; dependency mechanics go to the build-ci sibling |
