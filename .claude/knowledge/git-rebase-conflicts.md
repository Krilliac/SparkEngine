# Git Rebase Conflicts

**Last updated:** 2026-03-14
**Type:** Issue
**Status:** Resolved

## Issue

Rebasing feature branches onto `origin/Working` produces merge conflicts. Some conflicts are in auto-generated files where the right resolution is always "take upstream." Others are in hand-written code where careful judgment is needed. Getting this wrong either loses work or causes CI to fail on stale auto-generated content.

## Context

Occurs at two points:
1. **Session start** — rebasing onto latest `origin/Working` before starting any work
2. **Pre-commit** — rebasing before committing/pushing to ensure branch freshness

The repo has auto-generated content scattered across `docs/api/` and wiki pages. These files must not be hand-edited — they are regenerated by scripts (`docs/generate-api-docs.sh` and `docs/sync-wiki.sh`).

## Methods Tried

1. **`git rebase origin/Working` then manually resolving all conflicts** → WORKS but slow if you don't know which files to take from upstream automatically.

2. **`git rebase -Xours origin/Working`** → WRONG — "ours" in a rebase refers to the incoming upstream commits, not your branch. This is confusing and causes you to keep the wrong side.

3. **`git rebase -Xtheirs origin/Working`** → WRONG for code files — blindly takes upstream for all conflicts, discarding your branch's code changes.

4. **Selective strategy** (described below) → CORRECT

## Solution (Reliable Method)

Run the rebase, then handle conflicts file-by-file with a clear rule set:

```bash
git rebase origin/Working
# When conflicts appear:
git status   # see which files have conflicts
```

**Resolution rules by file type:**

| File pattern | Rule | Command |
|--------------|------|---------|
| `docs/api/**` | Always take upstream | `git checkout --theirs -- docs/api/` |
| `wiki/*.md` (only `<!-- AUTO:* -->` sections) | Take upstream for auto-sections, keep manual edits | Edit manually |
| `docs/sync-wiki.sh`, `docs/generate-api-docs.sh` | Take upstream | `git checkout --theirs -- docs/sync-wiki.sh docs/generate-api-docs.sh` |
| `SparkEngine/Source/**`, `SparkEditor/Source/**`, etc. | Resolve carefully — keep intent of your branch | Edit manually |
| `CLAUDE.md` | Merge carefully — keep both upstream additions and your additions | Edit manually |
| `CMakeLists.txt` | Merge carefully — don't drop either side's changes | Edit manually |

```bash
# After resolving all conflicts:
git add <resolved-files>
git rebase --continue

# After rebase completes, regenerate auto-generated docs:
docs/generate-api-docs.sh check
docs/sync-wiki.sh sync
```

### Auto-Generated Section Markers in Wiki Files

Wiki files contain markers like:
```
<!-- AUTO:component-list -->
... auto-generated content ...
<!-- /AUTO:component-list -->
```

When rebasing, conflicts in these sections should **always resolve to upstream** (take `--theirs`). Conflicts outside these sections in the same wiki file should be resolved normally.

To take upstream for just the auto-sections, open the file and manually accept the `<<<<<<< HEAD` / `>>>>>>> upstream` sections that fall within `<!-- AUTO:* -->` markers.

## Notes

- After any rebase, always run `docs/sync-wiki.sh sync` to ensure wiki auto-sections are current.
- If you accidentally took the wrong side for an auto-generated file, just re-run the generation script — it will overwrite the file with the correct content.
- The `--rebase-merges` flag is not needed for this repo — the history is linear on feature branches.
- If a rebase has many conflicts (5+ files), consider whether your branch has diverged too far. In that case, it may be worth doing a careful `git merge` instead of a rebase, then squashing before the PR.
- **Never** use `git rebase --abort` then force-push to skip a rebase. Always resolve conflicts properly.
