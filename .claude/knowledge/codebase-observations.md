# SparkEngine Codebase — Non-Obvious Facts

**Last updated:** 2026-03-14
**Type:** Observation
**Status:** Active

## Description

Non-obvious facts about SparkEngine's codebase structure, conventions, and tooling that are easy to get wrong. These are things not immediately apparent from reading CLAUDE.md or the wiki, or things that contradict common assumptions.

## Context

Applies to any development session on SparkEngine. These facts should be checked before making assumptions about how things work.

---

## Observation: Most Optional Systems Are OFF by Default

### Details

Several major engine systems are **disabled by default** in CMake. A build will succeed even if code in those systems is broken, because the code isn't compiled. The most common trap is networking:

```
ENABLE_NETWORKING=OFF   ← off by default
ENABLE_DXR=OFF          ← off by default (DXR raytracing)
ENABLE_VR=OFF           ← VR is implemented but disabled by default
```

If code in a disabled system silently breaks, it won't show up in standard CI builds. Conversely, if you're trying to test networking code and it "doesn't exist", check the CMake toggle.

### Notes

- To verify what's enabled in the current build: `cmake --preset linux-gcc-release -N` (dry run shows resolved options)
- CI does NOT enable `ENABLE_NETWORKING` — network-related CI failures must be from code paths that compile unconditionally
- **See also:** [build-optimizations.md](build-optimizations.md) for the CMake dry-run preset verification optimization

## Observation: Use EngineContext, Not Global Variables

### Details

Legacy globals like `g_graphics`, `g_input`, `g_audio` are **deprecated** and may be removed. All engine subsystems should be accessed via the `EngineContext` service locator:

```cpp
// WRONG — deprecated globals:
g_graphics->RenderFrame();
g_input->IsKeyDown(Key::Space);

// CORRECT — EngineContext service locator:
auto* graphics = EngineContext::Get<GraphicsEngine>();
auto* input    = EngineContext::Get<InputSystem>();
```

If you see code using the old globals, it's legacy code — don't propagate the pattern.

### Notes

- `EngineContext` is in `SparkEngine/Source/Core/EngineContext.h`
- If a subsystem you need isn't registered in EngineContext, check whether it needs to be added there

## Observation: `.claude/` Is Intentionally Visible to Claude

### Details

`.claude/` is NOT excluded from `.promptignore`. This is intentional — Claude needs to read these files at session start to load persistent context. Do not add `.claude/` to `.promptignore`.

Current `.promptignore` excludes: `ThirdParty/`, `Shaders/Compiled/`, `build/`, IDE config dirs, `.git/`, binary files, and `docs/html/` + `docs/xml/`. Everything else (including `.claude/`) is visible.

### Notes

- If Claude can't seem to find `.claude/index.md`, the issue is not `.promptignore` — check the working directory

## Observation: `docs/api/` Files Are Entirely Auto-Generated

### Details

Every file under `docs/api/` is generated by `docs/generate-api-docs.sh`. **Never edit these files manually** — any manual changes will be overwritten the next time the script runs.

To update API documentation, edit the Doxygen-style comments (`@brief`, `@param`, `@return`) in the **header files** in `SparkEngine/Source/`. The generation script extracts comments from there.

### Notes

- The script uses checksum-based caching (`docs/generate-api-docs.sh check`) — it only regenerates files whose corresponding headers changed
- Same applies to the `<!-- AUTO:* -->` sections in wiki files: they're written by `docs/sync-wiki.sh sync` and must not be hand-edited

## Observation: Wiki Files Mix Auto and Manual Content

### Details

Files in `wiki/` are **not** fully auto-generated. Most content is manually written. However, specific sections are auto-generated and wrapped in markers:

```html
<!-- AUTO:component-list -->
... generated content, do not edit ...
<!-- /AUTO:component-list -->
```

When editing a wiki file:
- Content outside `<!-- AUTO:* -->` blocks: edit freely
- Content inside `<!-- AUTO:* -->` blocks: do not edit — it will be overwritten by `docs/sync-wiki.sh sync`

During rebase conflicts in wiki files, always take upstream for the AUTO: sections. See [git-rebase-conflicts.md](git-rebase-conflicts.md).

### Notes

- Files that have AUTO: sections: `Entity-Component-System.md`, `Testing.md`, `SparkEditor.md`, `Home.md`
- To add a new wiki page: create the file in `wiki/`, then add it to `wiki/_Sidebar.md`
- **See also:** [git-rebase-conflicts.md](git-rebase-conflicts.md) for conflict resolution in AUTO: sections during rebases

## Observation: Two `tools/` Directories with Different Purposes

### Details

There are **two** tool directories at the repo root that are easy to confuse:

| Directory | Contents | Purpose |
|-----------|----------|---------|
| `tools/` (lowercase) | `SparkBuild-*` binaries, `validate-prompts.sh`, `update-sparkbuild.sh` | Build toolchain and CI scripts |
| `Tools/` (uppercase) | `spark-cli/spark_cli.py` | Developer CLI utility |

`validate-prompts.sh` (referenced in CI's `validate-prompts` job) lives in `tools/` (lowercase).

### Notes

- On case-insensitive filesystems (macOS), these may appear as the same directory — they are distinct on Linux/CI
- CI references `tools/validate-prompts.sh --ci` — always lowercase

## Observation: CLAUDE.md Pre-Commit Step 1 Is a Partial Check

### Details

CLAUDE.md's pre-commit checklist step 1 uses `head -50`:

```bash
find ... | head -50 | xargs clang-format --dry-run --Werror
```

This only checks the **first 50 files by modification time**. The CI `check-format` job checks **all files**. It is possible to pass the local check and fail CI.

Always use the full CI-matching command without `head -50` before pushing. See [clang-format.md](clang-format.md) for the exact command.

### Notes

- The `head -50` shortcut is intentional for quick pre-commit feedback during development; the full check is for final verification before push
- The CI command also includes `.hpp` files which the CLAUDE.md shortcut omits

## Observation: ThirdParty Is Git Submodules, Not Vendored Code

### Details

`ThirdParty/` contains git submodules, not directly committed code. After cloning, you must initialize submodules before CMake configure will succeed:

```bash
git submodule update --init --recursive
```

If a ThirdParty directory appears empty or CMake reports missing files under `ThirdParty/`, this is always the cause.

### Notes

- `ThirdParty/` is in `.promptignore` — Claude won't see its contents in context, which is correct (it's not project code)
- When pulling new upstream commits that add a new submodule, run `git submodule update --init --recursive` again
